# Работа с проектом

Проект находится на стадии прототипа. Изменения должны оставлять понятными границы между сбором ответов, разбором данных, состоянием и уведомлениями.

## Ветки

| Ветка | Роль |
| --- | --- |
| `main` | Основной снимок проекта для просмотра и публикации; пока не production-релиз |
| `develop` | База для дальнейшей разработки |
| `feature/<задача>` | Новая возможность |
| `fix/<задача>` | Исправление |
| `docs/<задача>` | Документация |

В исходном архиве созданы `main` и `develop`; при первой упаковке они указывают на один коммит. Ветки для отдельных задач создаются по мере работы, а не для декоративной истории. Изменения обычно направляются в `develop`, затем проверенный набор — в `main`.

## Изменения и проверки

Используйте короткие содержательные коммиты с префиксами `feat:`, `fix:`, `docs:`, `test:` или `chore:`. Не объединяйте переработку парсера и изменение визуального оформления без необходимости.

Для изменений логики добавляйте тесты в `tests/`. Автономная проверка выполняется командой `python -m unittest discover -s tests -v` в окружении, где доступен пакет. Workflow также проверяет импорты, Python- и shell-синтаксис и синтетическую демонстрацию.

## Что нельзя добавлять

- `.env`, токен Telegram, личный chat ID и другие учётные данные.
- Браузерный профиль, cookies, реальные снимки аккаунта и рабочий `state.json`.
- Скриншоты с личными окнами и данными.
- Виртуальное окружение, кэш Python и временные файлы.

Примеры должны быть вымышленными и минимальными. `.gitignore` помогает избегать случайного добавления файлов, но не заменяет просмотр состава коммита.
